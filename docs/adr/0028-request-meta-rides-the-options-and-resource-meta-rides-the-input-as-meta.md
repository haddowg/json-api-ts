# Request meta rides a write's options, and resource meta rides its input as `$meta`

A server can declare the top-level `meta` a write takes and its resource objects' own `meta`, so the client needed a place for each that every write already has. The top-level `meta` goes in the options object a write, an action and an atomic operation take, required when a member is, because it belongs to the request rather than the resource, and the resource object's `meta` goes in the flat input as `$meta`, mirroring `$pivot` on a linkage ref and `$meta` on a read, since a JSON:API member name can't start with `$`. Both ride the descriptor as format hints with an `additional` entry for an object the server opens, rather than generated interfaces, so they type the same way document, pivot and identifier meta already do.
